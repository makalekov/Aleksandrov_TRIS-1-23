## Реализованные маршруты

| Метод и адрес | Результат |
|---|---|
| `POST /api/cable-tickets` | Создаёт заявку, возвращает `201 Created` и ссылку на неё в `Location` |
| `GET /api/cable-tickets` | Возвращает список заявок, в том числе фильтр по `assigneeUserId` |
| `GET /api/cable-tickets/{id}` | Возвращает заявку (`200`) или `404`, если она не найдена |
| `PATCH /api/cable-tickets/{id}/assignee` | Назначает исполнителя новой заявке |
| `PATCH /api/cable-tickets/{id}/status` | Выполняет разрешённый переход статуса |

Метод `DELETE` не реализован. При создании клиент передаёт тему, участок и описание. Идентификатор, номер, начальный статус и автора назначает сервер.
На этапе этой лабораторной заявки хранились в памяти; сохранение в PostgreSQL добавлено позднее в ЛР10.

## Проверки и коды ответов

| Сценарий | Фактический результат |
|---|---|
| Валидный POST | `201 Created` |
| Тема короче 5 символов | `400 Bad Request` |
| GET по неизвестному ID | `404 Not Found` |
| Запрещённый переход статуса или назначение закрытой заявке | `409 Conflict` |
| Получение существующей заявки и списка | `200 OK` |

`title` ограничен 5–80 символами, `description` — 10–500 символами, `siteId` должен быть положительным. Переходы статусов: `New → InProgress` (только назначенный исполнитель), `New → Cancelled`, `InProgress → Closed` (только назначенный исполнитель). Назначать исполнителя можно только новой заявке; возврат к `New` запрещён.

В Postman-коллекции проверки `201`, `400`, `404` и `409` оформлены как тесты ответов; в отчёте фиксируется результат ручного прогона:

```text
POST валидной заявки       201 Created
POST с короткой темой      400 Bad Request
GET отсутствующего ID      404 Not Found
PATCH status без исполнителя 409 Conflict
PATCH assignee             200 OK
PATCH status InProgress    200 OK
PATCH status Closed        200 OK
```

## Обработка ошибок и логирование

Проверена неожиданная ошибка при создании заявки. Клиент получает безопасный ответ `500 ProblemDetails` с общим текстом; stack trace и детали исключения в HTTP-ответ не попадают. Сервер пишет структурированную запись с `siteId` и типом исключения, без содержимого запроса и stack trace в сообщении приложения. Полученная при проверке строка лога:

```text
CreateTicket failed; siteId=2; error=InvalidOperationException
```

Искусственный сбой использовался только для проверки и удалён из рабочего кода.

## Postman

Коллекция находится в `docs/api-collection/cable-tickets.postman_collection.json`. Она содержит сценарии создания, чтения, невалидной темы, отсутствующего ID, конфликтов статуса, назначения и успешных переходов. Созданный ID сохраняется в переменную коллекции `ticketId`.
